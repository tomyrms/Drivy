# Continuité du compte, du rattachement et des accueils — 17 octobre 2026

## Ruptures constatées et changements

1. **Noms saisis deux fois.** La création OIDC recevait prénom et nom, mais l’API ne retenait que le nom public. L’acceptation créait un dossier sans noms structurés ; le guide demandait donc à nouveau les mêmes informations. Les deux revendications signées valides sont maintenant proposées dans l’aperçu authentifié et insérées lors de la création du dossier, après « Rejoindre ». Aucun découpage du nom public, aucune lecture du dossier d’une autre école, aucun écrasement d’un dossier existant. Sans revendications valides, le dossier historique incomplet reste incomplet.
2. **Ouverture d’école répétitive.** Le nom du compte existant pouvait se perdre entre connexion et formulaire natif ; une réponse `/me` tardive n’était pas reprise. Le nom connu sert de valeur initiale et remplit encore le champ si la réponse arrive tard, tant que l’utilisateur ne l’a pas modifié ou effacé. Le rôle moniteur devient un choix explicite sur les deux surfaces. Le web passe directement du reçu durable au guide, et une identité d’école déjà valide ne réouvre pas sa première étape.
3. **Accueil du mauvais rôle.** Les onglets donnaient priorité à INSTRUCTOR alors que l’accueil choisissait STUDENT dès que LEARNER figurait dans les rôles. L’annuaire moniteur pouvait ne pas contenir le dossier personnel, voire être vide. L’accueil suit maintenant la destination terrain : INSTRUCTOR → STAFF, LEARNER sans INSTRUCTOR → STUDENT. L’annuaire moniteur reste un annuaire ; sa pagination ne décide plus si l’accueil STAFF existe.
4. **Code perdu autour de la connexion.** Dans l’app, « J’ai déjà un compte » fermait la feuille ; sur le web, le code ne conduisait pas jusqu’au rattachement. Le code renseigné est inspecté et conservé lors du passage à la connexion. Le web propose ensuite le même aperçu école/identité/notice et l’acceptation explicite ; l’élève retrouve l’école dans son compte sans retaper le code dans l’app.
5. **Guide personnel linéaire malgré des données complètes.** Un élève dont les noms sont déjà valides peut passer de « Bienvenue » à sa formation sans formulaire imposé. Le récapitulatif conserve une action volontaire de modification et un retour direct. La lecture du profil ne soumet aucune commande ; compléter l’accueil ne crée aucun accord GPS.
6. **Retour qui perdait une saisie.** Depuis le récapitulatif personnel, modifier les informations puis revenir réinitialisait silencieusement le brouillon. Le retour et la fermeture demandent désormais de continuer la modification ou d’abandonner explicitement ; revenir sans modification ne demande rien.
7. **Entrée bloquée pour un membre connecté.** Le web masquait « J’ai un code » dès qu’une école était liée et pouvait afficher une page vide au changement de compte. Le code reste accessible depuis les écoles et le changement de compte retrouve un formulaire utilisable. Pendant une acceptation incertaine, la commande et l’aperçu confirmé restent conservés pour vérifier le résultat sans doublon.
8. **Curseur déplacé pendant la saisie.** La recette intégrée a montré un nom de compétence contenant aussi sa description, puis un tarif dont le nom contenait le prix « 99 » alors que le champ Prix restait à 95. Le focus programmé au prochain rafraîchissement revenait sur le nom après le choix du champ suivant. Le même défaut a été reproduit dans les coordonnées scolaires en commençant par l’e-mail. Les ouvertures de ces éditeurs et les ajouts/retraits/déplacements de compétences appliquent maintenant le focus au commit du DOM. Les reproductions avec callbacks retardés échouent sur l’ancien code et passent sur le nouveau ; la recette versionnée vérifie focus et valeurs séparées des compétences et tarifs. Le lien profond vers le téléphone scolaire conserve sa cible. Le scénario de conflit tarifaire n’avait pas perdu les valeurs : la frappe avait été détournée avant son envoi.
9. **GPS refusé après une connexion récente.** La connexion par mot de passe ne produisait pas le claim signé `auth_time` exigé par l’API ; le lien de reprise renvoyait vers l’ancienne page du fournisseur. Le fournisseur enregistre maintenant l’heure de validation, et la confirmation reste dans le formulaire Drivy avec le même compte. L’activation GPS demande ensuite un clic explicite. [Cause, correction et preuves](re-authentification-gps-20261017.md).
10. **Commande d’une personne conservée au changement de compte.** Le magasin de commandes était indexé par école. Une reconnexion avec une autre personne de la même école pouvait conserver la demande précédente en mémoire. Le changement de personne purge les commandes et les saisies avant affichage ; une génération invalide les réponses tardives. Une reconnexion de la même personne conserve sa demande incertaine pour consulter le reçu.

Le nom suggéré lors d’une ouverture native reprend d’abord la création en cours, puis la personne connue, enfin un indice d’affichage de la session OIDC restaurée. Cet indice est borné et lié à la configuration et au sujet de la session ; il ne donne aucun droit, ne crée aucune personne et n’écrit aucun profil. Le nom est toujours modifiable avant ouverture. Le dossier personnel d’un compte à plusieurs rôles est chargé séparément de l’annuaire moniteur, avec purge au changement de contexte et rejet des réponses tardives.

## Contrats et persistance

Le contrat OpenAPI canonique 3.11.0 reste intact. L’extension `apps/api/contracts/g1c-invitation-preview.json` décrit les aperçus authentifiés : `profileIdentity` facultatif contient les deux noms structurés du compte ; l’aperçu par code ajoute `invitationId`, `schoolId`, `delivery: CODE`, `maskedEmail: null` et la notice de l’école. L’aperçu anonyme `/access-codes/preview` conserve sa projection minimale et n’expose aucune de ces informations supplémentaires.

Les revendications OIDC `given_name` et `family_name` signées sont validées séparément, sans découper `name`. L’acceptation crée les noms dans la même transaction que le nouveau dossier et l’adhésion ; une relecture n’écrit rien, une réinvitation ne modifie aucun champ existant. Le contact scolaire ne vient jamais d’une adresse non vérifiée. Aucun dossier d’une autre école n’est lu ou recopié et aucune migration n’est ajoutée. Le web conserve l’opération et son aperçu confirmé pendant une réponse incertaine ; le rejeu doit être confirmé par l’API avant d’annoncer un succès.

## Régressions intégrées ajoutées

### 1. Identité de l’élève réutilisée exactement

Dans `check-school-first-lesson.ts`, créer le compte avec `Élève Camille` et `De la Tour-Roux`. Lire l’aperçu avant acceptation, accepter, puis relire le dossier et les prochaines actions. Vérifier les valeurs structurées et le nom affiché exacts, aucune commande `UPDATE_ADMINISTRATIVE_PROFILE`, aucune action `PROFILE_ACTION_REQUIRED` et aucune étape de ressaisie. La formation, les disponibilités et la réservation conservent leurs prérequis réels.

### 2. Ouverture et guide de l’école sans doublon

Dans `check-school-opening.ts`, vérifier les valeurs préremplies au lieu de les retaper, puis cocher volontairement le rôle moniteur. Après une création dont la réponse est perdue, le reçu doit conduire à `/app/gestion/{schoolId}/apercu`, à Confidentialité. Les contrôles existants de sauvegarde, reprise depuis une autre session, erreurs et activation restent en place.

### 3. Accueils STAFF et STUDENT durables

`check-personal-welcome.ts` utilise les jetons en mémoire des comptes réellement créés dans la recette, puis les routes de l’app : lecture initiale, sauvegarde FORMATIONS, relecture au même numéro de version, revue avec DEVICE facultatif passé, terminaison, nouvelle lecture toujours COMPLETED. Aucune commande de profil n’est envoyée. Il s’agit d’une vérification de continuité API avec OIDC réel, pas d’une preuve de navigation SwiftUI ni d’autorisation système.

### 4. Code conservé jusqu’à l’acceptation

`check-school-code-entry.ts` est appelé après les recettes de première leçon et de formations. Une invitation réelle par code est créée pour un compte existant, puis une autre pour un compte neuf. Le chemin existant presse directement « J’ai déjà un compte » après saisie du code. Un troisième scénario connecte d’abord le compte devenu membre et vérifie que « J’ai un code » reste accessible depuis ses écoles. Accepter ce nouveau code conserve son identifiant de personne, l’intégralité du dossier scolaire et une seule formation, sans déconnexion ni doublon. Chaque scénario vérifie l’aperçu identité/école, aucun dossier créé par la lecture, confirmation obligatoire, rattachement relu par `/me`, noms exacts sans PATCH et disponibilité de l’entrée. Cette répétition dans la même école ne qualifie pas une navigation multi-école. Aucun code ni jeton n’est ajouté aux captures ou aux résultats de recette.

### 5. Cas natifs que le navigateur ne couvre pas

`NativeAccountTests.swift` couvre priorité du nom de création sur le nom connu, nom composé sans découpage, réponse tardive sans écrasement d’une saisie ou d’un effacement, rôle moniteur non présélectionné, code conservé à la connexion, code invalide et connexion sans code. Les tests de projection de rôles, de profil et les scénarios UI d’accueil sont complémentaires. Leur exécution requiert le runner Apple.
