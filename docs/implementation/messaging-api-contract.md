# Contrat API de travail, messagerie #65

**Statut : désactivé par défaut.** `registerMessaging(app, { pool, verifyToken, mode })` refuse toutes les routes avec `503 MESSAGING_NOT_ENABLED` sauf `mode: 'test-synthetic'` dans un processus `NODE_ENV=test`. Le transport est une enveloppe opaque, **pas un protocole E2EE validé**. Aucune clef, chiffrement, déchiffrement ni mise en service utilisateur n'est livré par ce contrat. Tous les chemins ci-dessous commencent par `/v1/schools/{schoolId}/messaging`; authentification OIDC et appartenance scolaire active relues par transaction. Réponses JSON `{ "data": ..., "context": ..., "requestId": string, "serverTime": ISO-8601 }`; erreurs `ApiError` via le gestionnaire commun. Les tests PostgreSQL sont préparés mais différés selon #84.

**Liaison au compte obligatoire sur chaque requête :** `X-Drivy-Expected-Person-Id: <scope.accountID UUID>` et `X-Drivy-Expected-Access-Epoch: <scope.accessEpoch entier positif>`. Le serveur compare ces valeurs à la personne OIDC et à l'époque de l'appartenance active de l'école, sans leur accorder de droit, et refuse 403 si elles diffèrent. Une réponse réussie inclut `{ "context": { "schoolId": UUID, "actorPersonId": UUID, "accessEpoch": number } }` au même niveau que `data`. Le client doit vérifier contexte et génération de son workspace **après chaque await** avant d'afficher ou conserver la réponse. Un ancien workspace ne peut pas envoyer dans le général de la même école sous le jeton d'un autre compte.

## Découverte et conversations

- `GET /contacts?limit=50&cursor={personId}` → `data: { contacts: [{ personId, displayName }], nextCursor: UUID|null }`. Tri par UUID, maximum 100. Uniquement moniteurs/élèves affectés (décision 2 du 23 octobre : plus de contact ADMIN dédié ; les anciennes lignes `messaging_admin_contact` n'accordent plus rien). Aucun email/téléphone. Le curseur est la dernière personne autorisée de la page et les droits sont recalculés à chaque demande.
- `GET /general/members?limit=50&cursor={personId}` → `data: { members: [{ personId, displayName, photoVersion: number|null, hasPhoto, isGroupAdmin }], nextCursor: UUID|null }`. `photoVersion` seulement si `drivy.person_photo_visible`. Participants actuels de la seule école. Ces identifiants peuvent servir à une mention, jamais à ouvrir une conversation privée sans affectation.
- `PUT /private/{personId}` → `data: { conversationId: UUID }`. Paire et école uniques, ouverture idempotente. `PUT /general` → même DTO, unique par école. Les deux commandes refusent les droits caducs.
- `GET /conversations?limit=50&before={conversationId}` → `data: { items: [{ id, schoolId, kind: "PRIVATE"|"GENERAL", peerPersonId: UUID|null, title, lastSequence, lastReadSequence, mutedUntil: ISO-8601|null, readStateVersion: number, unreadCount }], nextCursor: UUID|null }`. `readStateVersion` vaut 0 en l'absence d'état, puis 1 à la première écriture. `title` vaut « Général » ou le nom du pair issu de `messaging_contacts` tant que ce pair est autorisé; repli prudent « Conversation privée » si le nom manque. Aucun accès au profil hors contacts n'est ajouté. `unreadCount` exclut ses propres messages. Le silence et la lecture sont personnels, pas des reçus publics. `before` est exclusif, tri UUID descendant.

## Messages et progression

- `GET /conversations/{id}/messages?limit=50&cursor={sequence}` → `data: { items: [Message], nextCursor: string|null }`. Ordre de séquence décroissant, curseur exclusif, maximum 100.
- `GET /conversations/{id}/events?afterSequence=0&limit=50` → `data: { messages: [Message], nextAfterSequence: number, hasMore: boolean }`. Reprise pull ascendante des seules enveloppes encore autorisées. Ne constitue pas une garantie push ou de livraison à un appareil. Répéter le même curseur peut rejouer des messages; le client déduplique par `id`.
- `POST /conversations/{id}/messages` avec `{ clientMessageId: UUID, ciphertext: { scheme: string, keyId: string, payload: base64 }, mentionPersonIds?: UUID[] }` → `data: Message`. `scheme` est une étiquette de transport, **non une sélection de protocole serveur**. La clef et le sens du payload viennent de #67. Longueur `payload` 4 à 12 000 caractères, taille JSON sous la limite Fastify 16 384 octets avec les autres champs bornés. Maximum huit mentions distinctes, uniquement dans le général, des personnes membres actives. Aucun `@tous` implicite. L'intention est unique par conversation+émetteur. Même intention/mêmes octets et mêmes mentions → même message. Intention réutilisée avec autre contenu → 409 `INTENT_CONFLICT`. Envoi, compteur et écriture appartiennent à une seule transaction.
- `Message`: `{ id: UUID, schoolId: UUID, conversationId: UUID, sequence: number, clientMessageId: UUID, senderId: UUID, ciphertext: { scheme, keyId, payload }, mentionPersonIds: UUID[], acceptedAt: ISO-8601 }`.
- `PUT /conversations/{id}/read-state` avec `{ lastReadSequence: number, mutedUntil?: ISO-8601|null, expectedVersion?: number }` → `data: { lastReadSequence, mutedUntil, readStateVersion }`. `expectedVersion` est obligatoire **si `mutedUntil` est présent**; utiliser 0 sans état préalable et la version reçue ensuite. La mise à jour concurrente du silence avec version périmée échoue en 409 `READ_STATE_CONFLICT`. La progression seule ne demande pas de version, ne recule jamais et préserve le silence; `mutedUntil: null` l'efface seulement si la version correspond. Aucune lecture visible par autrui n'est inférée.

## Garanties et limites

Les autorisations privées sont recalculées depuis les appartenances, dossiers non archivés, formations/affectations actives et contacts ADMIN explicites. Le général ne donne aucun accès privé. Les mutations acquièrent des verrous sur les sources de droits, revérifient après attente, puis écrivent atomiquement. Une révocation bloque les nouveaux accès; aucun effacement de contenu déjà déchiffré par un appareil tiers n'est promis. Les **identifiants de mentions en clair sont des métadonnées visibles par le serveur** : leur acceptation et leur résidence restent à valider en #67/#68 avant toute activation. Les curseurs UUID/séquence ne sont pas liés cryptographiquement au contexte; chaque page recalcule ses droits, propriété de prototype à réévaluer. Pas de temps réel, média, clé E2EE, vote, push ou outil de modération dans cette fondation. L'attribution auditée des contacts ADMIN reste bloquée sans route ni privilège d'insertion. PostgreSQL et la migration doivent encore être exécutés et qualifiés en #84.

## Contrat v2 (décisions du 23 octobre 2026, migration `20261023b`)

Toutes les mutations sensibles sont contrôlées dans la base (fonctions `SECURITY DEFINER` sous verrou, RLS forcée) ; codes internes DV403/DV404/DV409/22023 traduits en 403/404/409 `MESSAGING_STATE_CONFLICT`/400.

- **Fin du lien.** Chaque membre a des liens numérotés (`messaging_member_link`) : lisible si `readable_after < sequence <= cut_sequence`. Toute lecture ou écriture synchronise les liens (`messaging_sync_links`) ; l'envoi resynchronise sous le verrou de la conversation, donc aucun message postérieur à la coupure n'entre dans la plage d'un ancien membre. Un ancien membre garde la conversation en liste et sa plage lisible ; écriture, réaction, épinglage, vote, suppression pour tous : 403. Un retour ouvre une nouvelle plage après la dernière séquence (pas de rattrapage de l'intervalle).
- `GET /conversations` ajoute `membersEpoch` ; `lastSequence` = dernière séquence lisible par l'acteur.
- `GET /conversations/{id}/members` → `data: { members: [{ personId }], membersEpoch }`. Membres à lien ouvert. `membersEpoch` +1 à chaque départ et chaque retour, inchangé à la première arrivée. Sert la rotation Megolm.
- `GET /conversations/{id}/messages` → ajoute `access: { canWrite, readableUntilSequence: number|null, isGroupAdmin }` et `readStates: [{ personId, lastReadSequence }]` (lectures visibles, décision 7 : autres membres à lien ouvert, plafonnées à la plage de l'acteur). Les messages « supprimés pour moi » sont omis.
- `Message` v2 : `+ replyToMessageId: UUID|null, deletedForEveryone: boolean, pinned: boolean, reactions: [{ emoji, personIds }], poll: { optionCount, multiple, closed, creatorId, votes: [{ optionIndex, personIds }] }|null`. `ciphertext` vaut `null` après suppression pour tout le monde (enveloppe effacée côté serveur).
- `POST /conversations/{id}/messages` accepte `replyToMessageId?` (message lisible et non supprimé, sinon 404) et `poll?: { optionCount: 2..12, multiple }` (question et libellés dans l'enveloppe). Les deux entrent dans l'empreinte d'idempotence.
- `DELETE /conversations/{c}/messages/{m}?scope=me|everyone` → `data: { messageId, scope }`. `me` : idempotent, possible en lecture seule. `everyone` : auteur, ou administrateur du groupe dans le général ; efface enveloppe, réactions, sondage et épinglage ; idempotent.
- `PUT|DELETE …/messages/{m}/reactions/{emoji}` (👍 ❤️ 😂 😮 😢 🙏) → `data: { messageId, emoji, active }`, idempotent.
- `PUT|DELETE …/messages/{m}/pin` → `data: { messageId, pinned }`. Privé : chacun des deux ; général : administrateurs du groupe.
- `PUT …/messages/{m}/poll/votes` `{ optionIndexes: number[] }` → remplace les choix de l'acteur ; `[]` retire le vote ; plusieurs indices seulement si `multiple` ; sondage clos : 409. `POST …/poll/close` : créateur seul, idempotent.
- `PUT|DELETE /general/admins/{personId}` : administrateurs du groupe seulement (défaut : administrateurs de l'école) ; retirer le dernier : 409. `DELETE /general/members/{personId}` : retrait (pas soi-même), lié à l'adhésion courante, coupe le lien et incrémente l'époque. Journal `messaging_general_audit` (`ADMIN_GRANTED`, `ADMIN_REVOKED`, `MEMBER_REMOVED`). Un membre retiré reçoit 403 sur `PUT /general`.
- `POST /reports` `{ clientReportId, conversationId, items: [{ messageId, ciphertext }] (1..50) }` → `data: { reportId, itemCount }`. Idempotent par `clientReportId` ; contenu différent : 409 `REPORT_CONFLICT`. Messages limités à la plage lisible du signalant (sinon 404). Enveloppes rechiffrées par le client pour les administrateurs de l'école. Limite de corps 640 Kio. `GET /reports?limit&before` (administrateurs de l'école) → `data: { reports: [{ id, conversationId, reporterPersonId, createdAt, items }], nextCursor }`.

Tests PostgreSQL écrits, non exécutés (#84) : `test/messaging-v2.integration.test.ts`.

## Relais de clés Matrix (Olm/Megolm, sans homeserver)

Préfixe `/v1/schools/{schoolId}/messaging/crypto`, mêmes en-têtes que la messagerie plus `X-Drivy-Device-Id` (`[A-Z0-9]{10,32}`). Réponse `{ data: <JSON Matrix brut>, context: { schoolId, actorPersonId, accessEpoch }, requestId, serverTime }`. L'appareil est lié au compte et à l'école au premier appel ; un appareil révoqué reçoit 403. Identifiants Matrix : `@{personId}:drivy`, salons `!{conversationId}:drivy`. Le serveur ne stocke que des clés publiques, des contenus to-device chiffrés et une sauvegarde chiffrée, jamais de texte ni de clé privée. Pairs visibles (`drivy.messaging_key_peer`, migration `20261023c`) : soi, contact privé autorisé, ou participant du Général (`messaging_general_participant`) si le Général existe ; les autres sont omis sans erreur. RLS forcée sur toutes les tables. Désactivé hors mode test synthétique (503).

- `POST keys/upload` `{ device_keys?, one_time_keys?, fallback_keys? }` → `{ one_time_key_counts }`. `device_keys.user_id/device_id` doivent être ceux de l'appelant ; changer les clés d'identité d'un appareil : 409 `DEVICE_KEYS_CONFLICT`. Clé à usage unique renvoyée identique : idempotent, différente : 409 `ONE_TIME_KEY_CONFLICT`. Bornes : 100 clés par envoi, 200 par appareil, 4 clés de repli.
- `POST keys/query` `{ device_keys: { userId: [deviceId] } }` → `{ device_keys, failures, master_keys, self_signing_keys, user_signing_keys }` (user_signing seulement pour soi). Appareils révoqués exclus.
- `POST keys/claim` `{ one_time_keys: { userId: { deviceId: algorithm } } }` → `{ one_time_keys, failures }`. Sélection et suppression dans une même instruction `FOR UPDATE SKIP LOCKED` : une clé n'est jamais distribuée deux fois ; à défaut, clé de repli marquée utilisée.
- `PUT sendToDevice/{eventType}/{txnId}` `{ messages: { userId: { deviceId|*: content } } }` → `{}`. Idempotent par (appareil émetteur, txnId) avec empreinte ; contenu différent : 409 `TRANSACTION_CONFLICT`. Destinataires non autorisés ou révoqués ignorés. 16 Kio par contenu, 500 destinataires.
- `GET sync?since=t{n}_d{m}` → `{ next_batch, to_device: { events }, device_lists: { changed, left }, device_one_time_keys_count, device_unused_fallback_key_types }`. File par appareil, 100 événements par page ; passer `since` acquitte ce qui précède. `changed` : pairs dont les clés ont changé, ou redevenus pairs ; `left` : personnes qui ne sont plus pairs depuis le sync précédent de cet appareil.
- `POST keys/device_signing/upload` (clé maîtresse jamais remplacée : 409 `CROSS_SIGNING_CONFLICT`) et `POST keys/signatures/upload` → `{ failures }` (signatures acceptées sur ses propres clés seulement).
- `GET devices` → `{ devices: [{ deviceId, createdAt, isCurrent }] }` ; `DELETE devices/{deviceId}` → `{ deviceId, revoked: true }`, idempotent : clés publiques, clés à usage unique et file supprimées, changement annoncé.
- `POST room_keys/version` `{ algorithm, auth_data }` → `{ version }` (nouvelle version courante) ; `GET room_keys/version` → `{ version, algorithm, auth_data, etag, count }` ou 404.
- `PUT room_keys/keys?version=` `{ rooms: { roomId: { sessions: { sessionId: data } } } }` → `{ etag, count }`. CAS : version non courante → 409 `BACKUP_VERSION_CONFLICT`. Une session existante n'est remplacée que par une meilleure (vérifiée, index plus bas, moins transférée). `GET room_keys/keys?version=` → `{ rooms }`, 5000 sessions au plus.

`GET conversations/{id}/members` (`membersEpoch`) est servi par `messaging-routes.ts`. Le runner de migrations accepte désormais un suffixe de lettre (`20261023b_`, `20261023c_`). Tests PostgreSQL écrits (`test/messaging-keys.integration.test.ts`), non exécutés : #84.
