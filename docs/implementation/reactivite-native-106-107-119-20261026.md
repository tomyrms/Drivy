## File scolaire : conflits explicites, migration prudente

`SchoolCommandDomain` identifie les dépendances connues. `pendingCommands(for:)` expose toute la file ;
`pending(for:domain:)` ne retourne qu'une demande conflictuelle. L'ancien `pending(for:)` garde sa barrière
prudente pour les parcours non encore adaptés. Les octets, versions, portée et identifiant de chaque commande
restent immuables ; la demande de retrait d'une observation garde sa transition atomique existante.

| Commandes | Domaine / dépendance | Persistance / reprise |
| --- | --- | --- |
| Création, renvoi, révocation d'invitation | Invitations ; sérialisation entre invitations | Coffre scolaire ; reçu AP72 et requête initiale |
| Préférences de planification | Préférences de planification | Même coffre, version de l'adhésion |
| Création/déplacement/annulation/démarrage, disponibilités, préparation, souhait, bilan, partage, observations | Pédagogie ; agrégats croisés conservés ensemble | Même coffre, contrats existants par commande |
| Configuration, activation, règles, catalogue, profil scolaire, formations, affectations et droits | Barrière scolaire | Même coffre ; aucun parallélisme déduit d'objets différents partageant une version |
| Capture et envoi des messages | Files spécialisées existantes | Inchangées ; jamais fusionnées dans le coffre scolaire |
| Préférences personnelles de notification | Compte + API, version commune aux quatre catégories | Journal de compte scellé ; réconciliation If-Match ci-dessous |

Les invitations et préférences de planification adoptent les domaines dans ce lot. Les autres appels sont
adaptés dans leur tranche métier. Une autre époque ou adhésion de la même personne/école reste bloquante
jusqu'à résolution de la demande ancienne : aucun rejeu implicite sous de nouveaux droits.

Les archives v1/v2 restent lisibles. L'archive v3 n'est écrite que si plusieurs domaines d'une école coexistent ;
les anciens binaires la refusent, au lieu d'ignorer une intention. Suppression de la dernière coexistence : le
format redevient v1/v2 selon son contenu. Le plafond de 50 commandes, AES-GCM, protection complète,
exclusion des sauvegardes, remplacement atomique et barrières de stockage sont conservés.

Cette première politique reste conservatrice au sein du domaine pédagogique. Le détail par leçon/formation
sera adopté avec les tickets de parcours, après inventaire de leurs versions partagées ; aucune promesse de
parallélisme universel n'est faite.

## Préférences : projection immédiate, une seule écriture par version

`SchoolNotificationSettingsModel` conserve la dernière réponse confirmée et au plus une intention par catégorie.
Chaque nouveau choix porte un identifiant local ; l'accusé d'un ancien choix ne retire pas le suivant.
Les interrupteurs restent utilisables pendant l'envoi. Un PUT regroupe un instantané des intentions et les
catégories intactes de la dernière réponse ; le suivant attend sa résolution et emploie la nouvelle version.

`EncryptedAccountIntentStore` conserve intentions et tentative exacte (corps, version, identifiants des choix)
avant émission. La clé est au Trousseau, AES-GCM lie le contenu à l'API/personne/usage, les fichiers sont protégés,
atomiques et synchronisés. La lecture d'un journal illisible interdit son remplacement par un journal vide.
Une erreur de stockage conserve le choix en mémoire, l'explique et interdit l'envoi tant que la barrière n'a
pas réussi. Il n'existe aucun repli en clair.

| Résultat | Comportement |
| --- | --- |
| Réponse validée | Appliquer la réponse, retirer seulement les intentions acquittées, garder les choix plus récents |
| Réponse perdue, illisible, coupure | Garder tentative et projection, afficher « non confirmée » ; action de vérification |
| GET après résultat incertain | Confirmer seulement les valeurs observées. Version identique : réutiliser corps/précondition exacts. Version avancée : préserver les catégories étrangères et reconstruire seulement les choix encore non reflétés |
| 412 | Relire ; prendre les catégories modifiées ailleurs, réappliquer les choix locaux restants sans ancien snapshot global |
| Refus métier certain | Retirer uniquement les intentions de la tentative refusée, conserver les suivantes et expliquer |
| Identité ou accès refusé | Retirer les données affichées ; garder la preuve incertaine sur disque, sans rejouer sous un autre compte |
| Compte changé pendant requête | Réponse ignorée, file en mémoire invalidée ; le client vérifie aussi la portée avant et après obtention/renouvellement du jeton |

La boucle est bornée à huit tentatives consécutives ; un conflit continu exige une reprise explicite. Après
10 secondes, l'interface annonce une synchronisation prolongée, sans considérer ce délai comme un rejet.
Les identifiants locaux du journal ne sont pas prétendus être des reçus serveur.

## Lectures et durée de vie

Le cache mémoire contient un seul modèle, par API/personne : quatre valeurs confirmées, quatre intentions au
plus et une tentative. Retour sur la page : projection immédiatement disponible puis GET ciblé. Aucune lecture
de toute l'école, aucun préchargement de dossiers, aucune copie de préférences en stockage clair. Les lectures
simultanées sont dédupliquées ; une révision locale invalide un GET commencé avant un PUT. Échec de refresh :
données conservées avec erreur et reprise. Premier chargement : état explicite, sans faux réglages par défaut.

La déconnexion purge ce cache et annule ses tâches ; le journal chiffré reste séparé par compte. Une reprise
après relancement attend une lecture autorisée avant affichage/envoi. Un changement d'école garde les préférences
personnelles ; il ne transporte aucun droit scolaire. Les réglages locaux d'apparence restent inchangés.
