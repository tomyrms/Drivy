# CI allégée

31 octobre 2026. Demande du porteur : les CI sont trop longues et testent des choses sans rapport avec le changement. Branche `claude/ci-allegee-20261031`.

Les chiffres marqués **mesuré** viennent des 600 derniers runs (21 au 31 octobre ; jobs et étapes de 495 runs, journaux de 154 runs iOS). Ceux marqués **estimé** sont des projections, à vérifier sur les premiers runs après fusion.

## Où partait le temps (mesuré)

Sur 10 jours : 5 235 minutes de jobs macOS (87 h) et 1 066 minutes Ubuntu.

| Poste macOS | Jobs | Minutes | Part |
|---|---|---|---|
| Parcours UI iPhone et iPad | 63 | 2 134 | 41 % |
| Tests métier iPhone | 64 | 1 035 | 20 % |
| IPA d'essai | 133 | 970 | 19 % |
| Campagne complète et IPA | 9 | 405 | 8 % |
| Parcours UI iPhone seul, captures | 18 | 370 | 7 % |

- Les parcours UI échouent dans 62 % des cas (39 sur 63) : 1 383 des 2 134 minutes ont servi à des runs rouges, relancés ensuite. Treize des 35 runs UI en échec n'avaient que des tests qui passent sur l'autre appareil dans le même run : de l'instabilité plutôt qu'une régression.
- Un job « Tests métier iPhone · all » dure 16,4 min (médiane) : compilation 6,3 min, démarrage du simulateur 143 s (médiane sur 209 démarrages, jusqu'à 461 s), puis 959 tests Swift Testing en **77 secondes**. La sélection par parcours (`unit_test_scope`) ne peut donc pas gagner grand-chose : la compilation et le démarrage dominent.
- La compilation du simulateur faisait le travail deux fois : 708 compilations Swift en arm64 et 708 en x86_64, alors que le runner et le simulateur sont arm64.
- La jambe iPad d'un parcours UI (fin de l'iPhone à fin de l'iPad, démarrage compris) coûte 12,9 min en moyenne (685 min sur 53 runs). Sur ces 53 runs, 2 seulement échouent sur l'iPad seul, et les deux tests concernés échouent aussi par intermittence sur l'iPhone dans d'autres runs.

## Attentes (mesuré)

Médiane d'attente avant démarrage : 4 s. Mais 40 runs sur 488 attendent plus de 1,5 min, 368 min cumulées :

- 28 runs (303 min, jusqu'à 51 min) attendaient un autre run du **même workflow sur la même branche** : le groupe de concurrence `refonte-ios-<branche>-<mode>` sérialisait les lancements, et GitHub annule en plus le lancement en attente quand un troisième arrive (une partie des 16 annulations iOS).
- 5 runs (24 min) tombaient sur au moins 4 jobs macOS simultanés. Le pic est de 6 ; le temps passé à 4 jobs ou plus est inférieur à 2 % : la limite de runners n'est pas la cause.
- **Les 59 minutes du run 41234908420 ne sont pas une file d'attente.** C'est une relance (tentative 2) : `created_at` est celui de la tentative 1 (19:35, échec à 20:25) ; la tentative 2 a démarré à 20:34:18, 4 secondes après la relance. Même lecture pour 40738918926 (tentative 3). Pour voir une vraie attente, comparer `created_at` et `started_at` du job de la même tentative.
- Le même mécanisme touche master : sur les deux IPA des fusions de 22:33 et 22:34, la seconde est restée en file derrière la première (groupe `ipa-essai-refs/heads/master`, sans annulation).

## Ce qui change

| Sujet | Avant | Après |
|---|---|---|
| Lancement sans paramètre de « Refonte · iOS » | campagne complète puis IPA non demandée (70 min, annulée) | refusé avant toute compilation |
| Suite UI ciblée | iPhone puis iPad | iPhone seul ; l'iPad avec `ui_ipad=true` |
| IPA en fin de campagne | toujours | seulement avec `build_ipa=true` (le workflow « IPA d'essai · iLoader » reste le moyen normal) |
| Groupe de concurrence iOS | par branche : attente jusqu'à 51 min | un groupe par lancement : aucun lancement n'en attend ni n'en annule un autre |
| Compilation du simulateur | arm64 et x86_64 | arm64 ; index d'éditeur et couverture de code désactivés |
| API et web sur push et pull request | toujours | seulement si un fichier modifié les concerne |
| Push ou pull request dépassé (vérifications, navigateur, IPA) | continue, master compris | annulé, master compris |
| Lancement manuel | partageait le groupe des push de sa branche | groupe à part : un push ne l'annule jamais |

Jamais annulés : un lancement manuel et la validation finale. Une qualification (`validation-finale.yml`) fournit un SHA : elle reste la campagne complète, iPhone et iPad, API et web, sans sélection.

### Master

L'IPA reste construite à chaque push de master qui touche l'application : c'est la seule compilation de l'arbre fusionné (celle de la branche porte un autre arbre). Sur 10 jours : 24 IPA sur master, 177 min, soit 3,4 % du temps macOS. Mais les fusions en rafale (cinq en 12 minutes le 31 octobre au soir) n'ont besoin que du dernier commit, qui contient tous les précédents : un push dépassé est donc annulé pour l'IPA, les vérifications et le navigateur. Contrepartie : un commit intermédiaire de la rafale n'a pas de statut propre ; en cas de rouge sur le dernier, relancer sur l'intermédiaire par un lancement manuel.

### Sélection des suites Ubuntu

`scripts/qualification/changed_domains.py` lit les fichiers modifiés (poussés, ou de la pull request). La suite « Contrats, droits et PostgreSQL » ne tourne pas si tous les fichiers sont étrangers à l'API ; « Web et BFF » ne tourne pas s'ils sont étrangers à l'API et au web (les tests web lisent `apps/api/contracts`). Tout tourne pour : workflows, `scripts/qualification/`, `package.json` et `package-lock.json` (n'importe où), `Package.resolved`, `.node-version`, `runtime-lock.json`, contrat OpenAPI, migrations, un chemin inconnu, une différence illisible. La vérification documentaire tourne toujours. Le résumé du job « Suites concernées par les fichiers modifiés » donne la décision et son motif.

## Mode d'emploi

```
# Tests métier ciblés (le temps varie peu avec le périmètre)
gh workflow run "Refonte · iOS" --ref <branche> -f unit_only=true -f unit_test_scope=agenda

# Parcours UI ciblé, iPhone seul (8 suites ou méthodes au plus)
gh workflow run "Refonte · iOS" --ref <branche> -f ui_test_suite="SchoolAgendaUITests/testMixedDayUsesOneChronologyAndOpensTheLesson"

# Le même, aussi sur iPad (mise en page large, rotation)
gh workflow run "Refonte · iOS" --ref <branche> -f ui_test_suite="LayoutContinuityTests" -f ui_ipad=true

# Captures (inchangé)
gh workflow run "Refonte · iOS" --ref <branche> -f visual_only=true -f visual_screens="agenda" -f visual_devices="iPhone"

# Campagne complète, sur demande explicite ; ajouter build_ipa=true pour l'IPA
gh workflow run "Refonte · iOS" --ref <branche> -f full_campaign=true

# IPA d'essai (inchangé)
gh workflow run "IPA d'essai · iLoader" --ref <branche> -f messaging_qualification=true
```

`[skip ci]`, `unit_only`, `visual_only` et ses options de captures, `messaging_qualification` fonctionnent comme avant. `ui_iphone_only` est conservé mais sans effet (l'iPhone seul est le défaut) ; il ne se combine pas avec `ui_ipad`. Le nom du job indique le mode : « Parcours UI iPhone seul », « Parcours UI iPhone et iPad », « Campagne complète », « Campagne complète et IPA ». Dans la validation finale, le job iOS s'appelle désormais « Campagne complète » (il ne construisait déjà pas d'IPA : celle-ci est un job séparé).

### Essai abandonné : démarrer le simulateur pendant la compilation

Les 143 s de démarrage de l'iPhone (médiane) semblaient masquables derrière la compilation. Essai sur le run 41247640168 : le simulateur qui démarre bloque les appels `xcodebuild` suivants (`xcodebuild -version` 76 s, `-showsdks` 77 s, contre moins d'une seconde d'habitude). L'étape « Générer le projet » passe de 0,8 à 5,3 min pour économiser environ 3 min plus loin : gain nul ou négatif. Retiré ; `test-simulator.sh` démarre l'appareil comme avant.

## Couverture

Retirée :
- **iPad par défaut sur une suite UI ciblée.** Gardé : `ui_ipad=true`, la campagne complète et la validation finale (`evidence.py` exige les preuves iPhone **et** iPad pour une qualification). Raison : 53 runs avec les deux appareils, aucune régression propre à l'iPad. Protection réduite : une mise en page cassée seulement sur iPad n'apparaît plus avant la campagne complète.
- **Couverture de code Xcode** : aucun consommateur dans le dépôt (aucune lecture de `xccov` ni de rapport). Réactivable en retirant `-enableCodeCoverage NO` de `refonte-ios.yml`.
- **Compilation x86_64 du simulateur** : jamais exécutée.
- **API et web sur un changement qui ne les touche pas** : voir la sélection ci-dessus.
- **Statut propre des commits intermédiaires d'une rafale sur master.**

Un seul test modifié : l'assertion sur la liste des périmètres métier de `test_test_selection.py` (elle ne connaissait pas `consent`, `drafts`, `profile` ajoutés par master ; elle échouait déjà sur master). Aucun test Swift, API, web ou navigateur supprimé, aucun code produit modifié.

## À trancher par le porteur

1. **iPad dans le contrôle UI courant.** Si une mise en page iPad doit rester surveillée à chaque correction, mettre `default: true` à `ui_ipad` dans `refonte-ios.yml` ; la jambe iPad revient (≈ 13 min).
2. **Rejouer seulement les tests en échec dans le même run** (`-retry-tests-on-failure -test-iterations 2`). Treize runs UI sur 35 en échec auraient été verts (554 min). Non retenu : cela masque l'instabilité et change ce que « vert » signifie pour une qualification. Possible pour les contrôles ciblés seulement.
3. **Réparer ou isoler les tests UI instables.** Les plus fréquents sur 10 jours : `testLoadOlderMessages` (9 échecs sur 20 exécutions iPhone), `testRefreshFailureRetainsCoursesAndSelectionUntilRetry` (8 sur 11), `testReactionFromLongPressClosesMenuAndUpdatesCapsule`, `testSearchInsideConversationFindsMessage`, `testFiveSecondResponseCannotReintroduceAQuicklyRemovedReaction`, `testMixedDayUsesOneChronologyAndOpensTheLesson`. C'est le plus gros gain restant, et il demande de modifier des tests.
4. **Runs iOS dépassés par un commit plus récent** : 20 runs, 348 min mesurées. Les lancements manuels ne sont pas annulés automatiquement (on ne sait pas lequel reste utile) ; `gh run cancel <id>` à la main.
5. **Push et pull request sur le même commit** : 9 commits vérifiés deux fois (≈ 69 min Ubuntu). Non touché : la pull request teste le résultat fusionné avec master.
6. **IPA sur master** : gardée (seule compilation de l'arbre fusionné). Si le porteur préfère ne la lancer qu'à la demande, retirer `master` de `on.push.branches` dans `ipa-essai.yml` ; la compilation du résultat fusionné ne serait alors plus automatique.
7. **Caches Swift** : non ajoutés. Les paquets se résolvent en ≈ 50 s, et Xcode invalide DerivedData à chaque checkout. Le dépôt utilise déjà 1,6 Go de caches.
