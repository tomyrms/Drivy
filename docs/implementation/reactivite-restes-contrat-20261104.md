Les noms ci-dessous sont une interface sémantique proposée, à adapter aux types existants ; ils ne prescrivent ni bibliothèque, ni nouvel endpoint, ni copie du moteur par fonctionnalité. Les tâches UI consomment ces capacités ; elles ne décident ni des droits ni du rejeu.

### L1 — Expiration, reprise et conservation

Entrée : intention immuable `(operationId, scope compte/API/école/adhésion/epoch, kind, target, baseVersion, bodyAvailability, createdAt, transmissionEvidence)`. Sortie : `recovery = verifyOnly | resendSame | reviewRequired | blockedByAccess`, `canLeave`, `durability = saving | protected | memoryOnly | failed`, motif français court. La date n'efface jamais la preuve d'une opération possiblement commitée. À relance, aucune commande temporelle/financière/d'accès ne part automatiquement : revalider portée et résultat, puis confirmation humaine si la demande reste admissible. Réessayer réutilise mêmes octets/version/clé ; modifier intention crée une nouvelle clé seulement après résolution de l'ancienne.

Ne pas inventer un TTL universel. Pour leçon : échéance = créneau demandé, déjà utilisé côté web par `lessonResendAllowed` ; offre/invitation : expiration/revocation serveur ; droits/consentement/finances : revue explicite à reprise ; texte réversible : rebase de version. Durée de rétention du brouillon chiffré après abandon/compte quitté reste une décision produit distincte du droit de renvoyer. Tant qu'elle n'est pas fixée, conserver protégé et ne pas rejouer automatiquement, ne pas annoncer une purge.

Le web rend `bodyAvailability=missing` après reload : vérifier reçu reste possible ; renvoyer ne l'est pas. Un échec sessionStorage doit rendre visible que le suivi ne survivra pas à la fermeture, sans jamais écrire les corps en clair. Migration : anciens formats lisibles, états transmis inconnus classés conservativement, fixture v1 remplie → nouveau client → ancien client, sans doublon ni perte. Un rollback n'efface pas les commandes ajoutées.

Tests requis : horloge avant/après échéance ; reload sans corps ; ancien coffre ; clé indisponible/disque plein ; refus 403/epoch ; réponse 404 puis commit tardif ; 429/Retry-After ; réponse mal formée ; reprise sans effet secondaire répété. Fichiers propriétaires de logique : command-store/core et stores natifs, par lots séquentiels ; les vues ne doivent pas appeler directement un renvoi en contournant cette politique.

### L2 — Annulation avant envoi, jamais annulation fictive en vol

`cancelUnsent(operationId, scope)` retourne `cancelledBeforeSend | alreadyHandedToTransport | storageFailure`. Transition atomique avec la prise par le transport. Succès seulement après retrait durable et absence démontrée d'émission ; si transmis/inconnu, proposer « Vérifier le résultat » / « Arrêter le suivi », jamais « Annulé ». Le `remove` actuel du coffre et le `release` web ne prouvent pas cette absence d'émission. L'arrêt du suivi reste une décision locale explicitement distincte de la commande compensatrice métier.

Tests : barrière exacte entre persistance et transport ; annulation gagne/perd la course ; échec de retrait ; kill/relaunch entre phases ; dependent parent/enfant ; aucun paquet envoyé quand annulé avant envoi. Les stores actuels émettent immédiatement après save/submit : ne pas ajouter un bouton Annuler universel tant que cette capacité n'existe pas.

### L3 — Réconciliation par champ et ordre des intentions

Consommateur reçoit `base`, `latestConfirmed`, `sentPatch`, `localEditsAfterSend`, `conflictedFields`, `confirmation` et `needsRefresh`. Champ local inchangé depuis base → prendre version serveur ; champ local seul modifié → garder ; champ changé des deux côtés différemment → conflit explicite, aucune restauration globale. Une intention suivante reste appliquée à la projection même si la précédente est refusée. `confirmed + needsRefresh` reste confirmé ; bouton « Actualiser », pas renvoi de l'écriture. Une version d'onboarding différente ne justifie pas silencieusement la destruction de texte encore autorisé : relire les champs admis, comparer et présenter la revue, sans réappliquer une permission ni une case de conditions.

Tests : saisie B pendant envoi A, modification externe d'un troisième champ, conflit du même champ, succès A/relecture ratée, réponses inversées, retrait A avec B conservée. Réutiliser setup-save-queue, useDraft.markSaved et les tests de profil ; la comparaison JSON du draft complet n'est pas un merge par champ général.

### L4 — Sortie sûre, identité et brouillons

État consommateur : `localMask`, `localSecrets = cleared | failed | pending`, `bffSession = closed | unknown`, `providerRevocation = confirmed | failed | notAttempted | unknown`, `devicePushRevocation` séparé. Aucun de ces états n'implique « toutes les autres sessions fermées ». Le web masque immédiatement après intention de sortie, invalide générations/cache, garde une voie de connexion indépendante ; si réponse perdue, statut de fermeture serveur inconnu, aucune restauration automatique des données anciennes. iOS traite explicitement le trajet avant masque ; arrêt local ne dépend pas du serveur et ne redémarre pas au retour réseau.

Intégrer réellement le cycle de brouillon A7 : flush avant fermeture ordinaire si nécessaire, abandon retire seulement après succès de stockage, logout applique la politique de purge du même compte avant de perdre son handle ; échec annoncé sans retarder indéfiniment le masque. Aucune refonte d'A7. Test du geste Root→fermeture→nouvelle session→coffre, pas simple appel du helper. Distinguer `AppLock` (session conservée), déconnexion Trousseau/BFF et révocation fournisseur/push. La capacité push sans token suggérée dans l'audit reste logique #74, pas UI #120, et son contrat de sécurité doit être traité par son propriétaire.
